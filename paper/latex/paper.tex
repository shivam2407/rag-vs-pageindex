\author{Shivam~Rawat

\begin{abstract}
Retrieval-Augmented Generation (RAG) pipelines typically rely on dense vector similarity to locate relevant document chunks. PageIndex, a recent alternative, organizes documents into hierarchical trees and uses LLM-guided traversal for retrieval, reporting 98.7\% accuracy on the FinanceBench benchmark---but from a single domain under the authors' own evaluation. We compare three retrieval strategies across four document QA domains (600 questions total) with a shared LLM backbone that isolates retrieval as the sole variable. Our central finding: hierarchical retrieval's apparent large advantage on financial documents (judge score 3.94 vs.\ 1.69 for dense RAG, $d$=1.16) is primarily a retrieval \emph{coverage} artifact. Dense RAG returns ``NOT FOUND'' for 53\% of financial questions; hierarchical retrieval always selects content from the tree. When we restrict to questions both systems answered, the gap collapses from 2.25 to 0.31 points. Conversely, dense RAG dominates on short technical passages (3.93 vs.\ 1.75, $d$=$-$1.09), where hierarchical retrieval's tree structure adds overhead without benefit. No system wins overall ($p$=0.58). We argue that the hierarchical-vs-vector choice is better understood as a coverage-precision tradeoff, modulated by document length and structural richness, than as an accuracy comparison.
\end{abstract}

Retrieval-augmented generation, document question answering, hierarchical retrieval, PageIndex, information retrieval, LLM evaluation

\section{Introduction}
\label{sec:intro}

Ask a RAG system to find a specific number in a 200-page financial report and it will often fail. The problem is well-studied but stubbornly persistent: when a question targets a particular line item---say, Walmart's days payable outstanding in FY2018---the relevant chunk may sit in a table with headers like ``Accounts Payable'' and ``Cost of Goods Sold,'' sharing almost no semantic overlap with the question. A 1000-character chunk around that table row just does not embed close to ``What is the DPO?'' in vector space.

PageIndex~\cite{pageindex} tries something different. It builds a tree over the document---leaves hold paragraph-level text, parents hold LLM-generated summaries of their children, and a root node summarizes everything. At query time, the LLM walks this tree from the top, picking branches that look relevant to the question. VectifyAI reports 98.7\% accuracy on FinanceBench~\cite{financebench} with this approach, which is striking. But the evaluation covers one domain, run by the people who built the system.

That is a strong number, and if it holds across other document types, it would be a clear win for hierarchical retrieval. Three questions seem worth asking:

\begin{itemize}
\item[\textbf{RQ1.}] Does hierarchical retrieval outperform vector-based retrieval beyond finance---on legal, scientific, and technical documents?
\item[\textbf{RQ2.}] Under what document characteristics (length, structural richness) does each approach win?
\item[\textbf{RQ3.}] What is the token cost per correct answer for each approach?
\end{itemize}

We ran the experiment. Three retrieval systems, four domains, 150 questions each, same LLM everywhere. The result that surprised us most was not about which system ``wins'' (no system does, overall: $p$=0.58). It was about \emph{why} one system looks like it wins on finance. The apparent large effect ($d$=1.16) is mostly an artifact of retrieval coverage: hierarchical retrieval always pulls out some text from the tree, while dense RAG says ``NOT FOUND'' 53\% of the time when no chunk is similar enough. Filter out those NOT FOUND cases and the gap drops from 2.25 points to 0.31. That changes the story considerably.

So the real question for practitioners is not ``which method is more accurate?'' but ``which coverage-precision tradeoff fits my documents?'' We think that framing is more honest about what the numbers show.

Our contributions:
\begin{enumerate}
\item To our knowledge, the first independent cross-domain evaluation of hierarchical tree retrieval vs.\ dense RAG, spanning four document types.
\item A coverage-conditioned analysis revealing that raw effect sizes from single-domain evaluations are primarily driven by retrieval coverage differences, not answer quality.
\item A cost-efficiency analysis normalizing token expenditure by accuracy, showing that the most efficient system depends on the domain.
\item An error taxonomy ($n$=102) categorizing failure modes by retrieval strategy.
\end{enumerate}

\section{Background and Related Work}
\label{sec:related}

\subsection{Retrieval-Augmented Generation}

Lewis et al.~\cite{rag} introduced RAG as a way to ground LLM responses in retrieved evidence. The standard pipeline is straightforward: chunk the document, encode chunks with a dense model~\cite{sbert}, throw them into FAISS~\cite{faiss}, and retrieve the top-$k$ at query time. Since 2020, dense retrieval has gotten much better. ColBERT~\cite{colbert} introduced late interaction; ColBERTv2~\cite{colbertv2} made it practical. BGE-M3~\cite{bgem3} merged sparse and dense signals into one model. HyDE~\cite{hyde} took a different tack entirely, generating a hypothetical answer first and using \emph{that} as the query embedding. We mention these because the coverage problems we find for basic dense RAG might look different with newer embeddings---something we revisit in Section~\ref{sec:limitations}.

\subsection{BM25 and Sparse Retrieval}

Robertson and Zaragoza~\cite{bm25} formalized BM25, and it refuses to die. Term frequency, inverse document frequency, no neural anything---yet it regularly beats dense retrieval on specialized corpora~\cite{lin2021}. The reason is simple: when a query contains a rare domain term like ``days payable outstanding,'' BM25 matches it directly. Embedding models often do not.

\subsection{Hierarchical Tree Retrieval}

PageIndex~\cite{pageindex} takes a different approach to indexing. During construction, it chunks a document into leaf nodes, then has an LLM merge and summarize adjacent pairs to form parent nodes, repeating upward until it reaches a single root. At query time, the LLM reads the root summary, picks a branch, reads that summary, picks again, and eventually lands on a leaf.

RAPTOR~\cite{raptor} had a similar idea, independently. The main difference: RAPTOR clusters chunks rather than merging adjacent pairs, and at retrieval time it searches across all tree levels at once instead of walking top-down. Sarthi et al.\ saw gains over flat retrieval on NarrativeQA and QASPER. We followed PageIndex's top-down approach but focused on a different question---not ``does tree retrieval work?'' but ``why does it appear to work so much better on some domains?''

Self-RAG~\cite{selfrag} is relevant here too, though from a different angle. It lets the LLM decide whether to retrieve at all. That connects to our finding that coverage---does the system even \emph{try} to answer?---matters as much as the quality of the answer when it does.

One thing worth flagging about the architecture difference: vector retrieval does one similarity computation over all chunks. Tree retrieval makes multiple LLM calls, one per level. That is slower, but it can be more precise when the document has clear internal structure---sections, subsections, tables---that the tree mirrors.

\subsection{Evaluation}

We follow the LLM-as-judge approach~\cite{mtbench}: a stronger model scores each answer on a 0--4 rubric. Several RAG evaluation frameworks exist---RAGAS~\cite{ragas}, FRAMES~\cite{frames}, CRUD-RAG~\cite{crudrag}---but our focus is on comparing retrieval strategies, not evaluation methods.

\section{Methodology}
\label{sec:method}

\subsection{Systems Under Comparison}

All three systems share an identical LLM backbone (GPT-4o-mini, OpenAI, accessed via GitHub Copilot API) with temperature=0 and max\_tokens=256. The only difference is how context reaches the LLM. Table~\ref{tab:systems} summarizes the design.

The hierarchical system replicates PageIndex's algorithm as described in Section~3 of~\cite{pageindex}: documents split into leaf nodes, adjacent pairs merged and summarized by the LLM to form parent nodes, parent summaries merged into a root. We implemented this ourselves rather than using the official codebase---a limitation we discuss in Section~\ref{sec:limitations}. Tree construction required 370 LLM summarization calls across all four domains.

\subsection{Evaluation Protocol}

\textbf{Primary metric: LLM-as-Judge.} A separate, stronger LLM independently scored each predicted answer against the gold answer on a 0--4 scale (4=fully correct; 3=mostly correct; 2=partially correct; 1=marginally relevant; 0=wrong or hallucinated). We chose LLM-as-judge over pure F1 because F1 penalizes correct paraphrases~\cite{mtbench}. We report F1 and exact match as supplementary metrics.

\textbf{Judge reliability.} We double-scored a 10\% holdout (60 answers) in a second independent pass. Overall weighted Cohen's $\kappa$=0.98, Spearman $\rho$=0.97. We note that score distributions are bimodal (concentrated at 0 and~4), which inflates agreement on extreme cases. We could not independently assess reliability on borderline scores (1--3) due to small borderline sample sizes.

\textbf{Binary accuracy.} Given the bimodality, we also report the fraction of answers scoring $\geq$3 as a more robust measure than the ordinal mean.

\subsection{Statistical Analysis}

We use paired Wilcoxon signed-rank tests with Bonferroni correction for four simultaneous domain tests (adjusted $\alpha$=0.0125). Effect sizes are Cohen's $d$. Bootstrap 95\% confidence intervals use 10,000 resampling iterations (seed=42).

\textbf{Power.} At the Bonferroni-corrected $\alpha$=0.0125, detecting $d$=0.3 with 80\% power requires $n$$\approx$130. Our $n$=150 per domain exceeds this threshold.

Dense RAG returns NOT FOUND for 53\% of financial questions. Every one of those scores zero, dragging the unconditional mean down to~1.69. When we look at just the 70 questions RAG actually answered, its mean jumps to~3.63. To control for selection effects, we also computed hierarchical retrieval's score on those same 70 questions: 3.94. The gap on the common answered set is 0.31---a far cry from the raw 2.25.

The same pattern flips on technology. There, hierarchical retrieval returns NOT FOUND for 55\% of questions, while dense RAG answers 99.3\%. On the questions hierarchical retrieval does answer, it scores 3.87---essentially matching RAG's 3.95.

What this boils down to: the two approaches differ in \emph{when they can retrieve}, not \emph{how well they answer}. Tree traversal handles structured, long documents where coarse summaries can route the LLM to the right section. Dense search handles short, keyword-rich passages where embedding similarity is enough.

\subsection{Failure Modes}

We sampled and classified 102 failure cases (answers scoring 0--1, up to 10 per domain-method cell) into six categories using an LLM classifier. Entity lookup failures account for 70\% of all errors, consistent across systems. BM25 is especially prone to these (31 of 40 BM25 failures) because entity names in the question may not match the document's terminology. Dense RAG shows more numerical reasoning failures (8 of 32 vs.\ 3 of 27 for hierarchical), possibly because tree traversal preserves the context surrounding tables where numbers appear.

\section{Discussion}
\label{sec:discussion}

\subsection{The Coverage-Precision Tradeoff}

The numbers in Section~\ref{sec:results} point to a structural explanation. Hierarchical traversal forces the LLM to commit to a branch at every tree level. It always ends up at a leaf node with text---that is how trees work. Whether that text is relevant is another question. Dense RAG, by contrast, can fail gracefully: if no chunk is similar enough, the generation LLM says so. One approach guarantees coverage at the cost of precision; the other guarantees precision at the cost of coverage.

On financial reports, coverage wins. The documents are long, they have clear sections (Income Statement, Balance Sheet, Notes), and the tree structure mirrors this organization. On short tech passages, coverage is free---dense retrieval can already find the answer 99\% of the time---so the tree just adds latency. Fig.~\ref{fig:tradeoff} plots each domain in the accuracy-gain vs.\ cost-ratio space, making the tradeoff visible at a glance.

\subsection{What This Means in Practice}

The recommendation depends on what you are building. Long, structured documents with section headings (financial reports, regulatory filings, big technical manuals)? Hierarchical retrieval's coverage advantage probably justifies the extra indexing cost. Short documents, or documents you expect to chunk cleanly? Dense retrieval is simpler and works fine.

A caveat, though. We used all-MiniLM-L6-v2 for the dense embeddings---a 22-million-parameter model released in 2021. That is not what anyone would use today. BGE-large, E5-mistral, GTE-Qwen2: any of these would produce better embeddings, and hybrid systems that combine BM25 with dense signals~\cite{bgem3} would further close the gap. Our experiment tests the \emph{architectural} tradeoff (tree vs.\ flat), not any particular implementation. A modern dense pipeline might not have a 53\% NOT FOUND rate on financial questions. We do not know; we did not test it.

It is also worth being upfront about the legal and science domains. All three systems scored below 0.50 on both. At that level of performance, we are comparing noise, not systems.

\subsection{Limitations}
\label{sec:limitations}

The biggest threat to our conclusions is that we did not use PageIndex's actual code. We reimplemented their algorithm from the paper description, and our tree construction may well differ from theirs in ways we cannot verify. Testing with the official codebase, and with RAPTOR~\cite{raptor}, is the obvious next step.

Our dense retrieval pipeline is also dated. All-MiniLM-L6-v2 is small, old, and not representative of what a modern RAG stack would use. The 53\% NOT FOUND rate on finance might drop substantially with better embeddings or larger chunks. (We used 1,000-character chunks throughout, and chunk boundaries that split a table in half will obviously hurt retrieval.)

The technology dataset is a weak point. SQuAD-Tech passages average 812 characters---short enough that a single chunk often contains the entire passage. Dense RAG's 98\% accuracy there probably reflects how easy the task is, not some intrinsic advantage of embedding-based retrieval on technical content.

Two more things worth stating plainly. First, we used one LLM for generation and one for judging. A stronger generator might compensate for bad retrieval; a different judge might score differently. Second, we report token cost but not latency, and for production use the sequential LLM calls in tree traversal are a real concern that our cost-per-question numbers do not capture.

\section{Conclusion}

We tested three retrieval strategies on 600 questions across four domains. None won overall. Hierarchical tree retrieval dominated on structured financial documents; dense RAG dominated on short technical passages. The thing that surprised us, and that we think matters most for practitioners, is the coverage decomposition: strip out the NOT FOUND cases and the accuracy gap between systems nearly vanishes. The systems are not really competing on answer quality---they are competing on whether they can find the answer at all. Which one you should pick depends on your documents.
